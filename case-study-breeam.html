BREEAM Evidence-Matching Tool

A tool that reads a project's evidence documents and shows which BREEAM criteria each one supports, with page citations. I rebuilt it from scratch after the first version's retrieval step kept breaking in ways that were hard to patch.

ForA BREEAM assessor at Max Fordham
My roleDesigned and built the tool; ran the scoping session with the assessor
Scope421-page manual, 10 categories, about 49 issues
StackPython, PyMuPDF, swappable LLM providers

Problem

BREEAM assessors collect evidence from clients over months: transport assessments, workshop notes and similar documents. Each one has to be matched by hand against the criteria in the 421-page BREEAM UK New Construction manual to see what is actually supported.

The tool does that cross-referencing and produces a spreadsheet of which criteria have supporting evidence and where, with page citations. It is deliberately not a credit-scoring tool. The assessor still decides what counts.

I looked at the existing tools first (IES TaP, and Tracker Plus from Southfacing). Both are project-management and tracking tools. Neither judges evidence against a criterion automatically, which is the gap this tool fills.

Approach

The first version, and why I dropped it

The first pipeline used TF-IDF chunk retrieval. It had two specific bugs: sentence splitting broke on decimal section numbers like "3.1", and the chunk store silently overwrote chunks from the same page. Patching around them would have left the same kind of bug waiting elsewhere, so I restarted the architecture to remove the whole class.

No chunking, no embeddings, no vector store

The documents in this domain are tens of pages, well inside a modern LLM's context window. Retrieval was solving a "corpus too big to fit" problem that this project does not have. Now each evidence document is read in full with PyMuPDF and matched against a whole BREEAM category chapter in a single model call. With no chunk boundaries, that bug class cannot occur.

Criteria are read from the manual, not hand-transcribed

An earlier iteration used a JSON file of criteria I had transcribed by hand. Transcribing about 49 issues is as much manual work as the tool is meant to save, so the model now reads criteria numbers and descriptions straight from the manual's own text. All 10 categories work immediately, and the tool cannot drift from the manual's wording.

Verification that never trusts the model

Every citation the model produces is checked mechanically against the source (verify_quote()). One bug this catches: models often cite a document's printed page number rather than the PDF page, and the two are commonly offset (in one real evidence document, printed page was PDF page minus 6). The verifier ignores the claimed page, checks the page it claimed and the pages either side first, then searches the whole document and reports where the quote was actually found. A fuzzy-match fallback (longest common substring, threshold 0.85) handles quotes that are not perfectly verbatim.

Uncertain findings are shown, not hidden

At first, unverified findings were discarded. I changed this: the assessor should see everything the model found and judge it herself. Verified findings get their page silently corrected, and unverified ones are flagged inline ([UNVERIFIED - quote not confirmed in source text, please check manually]) instead of being removed.

Confidentiality built in

The LLM provider is swappable behind one interface and selectable in the sidebar. The long-term aim is a fully local model through Ollama, because hosted APIs should not see real client documents. For a hosted deployment, the API key lookup runs server-side only, and a locked-mode environment variable removes the provider and key picker from the UI.

Scoped with the actual user

I ran a structured planning session with the assessor. It confirmed one spreadsheet per project, named by BREEAM evidence reference number plus document description, matching how she files things. It also surfaced something I would not have known: a project's Scoresheet lists only the credits that project is targeting, not all 49 issues. The tool now checks only the relevant credits by default.

Outcome

The rebuilt tool has been tested against real planning documents from the Cambridge Whittle Laboratory project. It produces the evidence-to-criteria spreadsheet with page citations, and every citation in it is either confirmed against the source or visibly flagged.

I have not put a usage or time-saved figure on this page because I do not have a measured one.

What changed along the way

  • Moved from chunked TF-IDF retrieval to full-context judging, after two bugs showed the retrieval step was solving a problem the project did not have.
  • Moved from hand-transcribed criteria to reading them live from the manual, because the transcription did not scale.
  • Moved from dropping unverified findings to flagging them, after deciding the assessor should make the call.

Roadmap, phased on purpose. Phase 1 is core evidence checking, scoped per project via its Scoresheet, as a spreadsheet that updates as evidence arrives. Phase 1.5 is an on-demand missing-credit report. Phase 2 adds logins and a basic audit trail. Phase 3 is role-based access control, deliberately deferred until real usage shows what needs restricting. Phase 4 generates the full Planning Report, a larger deliverable built on top of the evidence spreadsheet.
